# 每日更新搬到 GitHub 雲端 runner，由新增的比分服務準時觸發

每日更新原本跑在使用者筆電 WSL 的 self-hosted runner 上，理由是「官網有 Cloudflare，雲端 runner 進不去」。賽事全在週末，筆電週末不開，賽果要到週一才進站（#196 當時接受了這一點）；推播上線後，賽果摘要也跟著週一才發。要改成比賽當天進站，而且不靠筆電開機。選項：(a) 筆電週末開著；(b) 家裡擺一台常開的機器或租主機；(c) GitHub 雲端 runner。決定 **(c)**，並**新增比分服務**負責準時觸發。這取代 ADR 0015「只為推播新增一個發送服務」那一句：執行期服務從一個變成兩個。

- 每日更新整條搬到 `ubuntu-latest`，平日也搬。筆電 runner 留兩個比賽週末當備援（手動觸發時選 runner，不做自動切換）；這段期間雲端沒被官網擋過，就把筆電 runner、本機觸發 timer 與那把 PAT 一起退役。
- 觸發由比分服務做：每天台北 09:23 跑整包；當天有賽事時，另在 15:30、18:30、21:15 各跑一次精簡版。當天有沒有賽事讀站上的推播賽事檔，不寫死星期幾。
- 精簡版只抓當天場次的比分與單場數據，再重算賽前勝率；不重掃全季、不抓名單與賽事列表。
- GitHub 自己的排程留作備援，晚到時先檢查過去一天有沒有被準時觸發過；沒有就照樣跑完更新，再讓那次 run 失敗，由 GitHub 寄信。
- 賽果摘要仍在賽果進站後才發，所以一個比賽日最多發三則。

雲端 runner 的依據：2026-11-19 從 `ubuntu-latest` 用爬蟲同一組 headers 抓官網 `/game/343`、`/schedule`、`/wgame/289`，三次都回 200、內容完整（run 44462957835）。同一天實測，官網擋的是 UA：curl 預設 UA 回 Cloudflare 的 403 封鎖頁，瀏覽器 UA 回 200。「雲端 runner 進不去」在 repo 與 issue 裡都找不到當時的狀態碼或做法。取樣只有一次、一個 IP，所以才留兩個週末的備援期。

不靠 GitHub 排程準時觸發的理由：這個 repo 實測排程建立時間比 cron 晚 4–7 小時，也曾整次沒觸發（#196），比賽日的三個時間點撐不住。Cloudflare 的 cron 準到分鐘，發送服務已經在用。

觸發不放進發送服務的理由：發送服務保管推播私鑰與推播訂閱，不該再多一把能動 repo 的 token。比分服務之後還要提供即時比分（另立 ADR），名字與邊界跟著那個職責走。

下午與晚上跑精簡版的理由：整包一次約 360 次請求、9–11 分鐘，一個比賽日跑四次約 1,400 次請求，絕大多數頁面沒有變。

## Consequences

- 執行期服務有兩個：發送服務與比分服務，都在 Cloudflare Workers，各自部署。網站本身仍是純靜態。
- 比分服務存一把 GitHub token，權限只限觸發本 repo 的 workflow。它會到期，到期或失效時靠上面的備援排程補跑並寄信。
- 雲端 runner 每次都是乾淨環境：Python 依賴要在 workflow 裡安裝，`.db` 仍然 commit 回 repo，建置部署照舊由 `pages.yml` 做。
- 官網哪天開始擋雲端機房的 IP，每日更新會整條失敗。備援期過後沒有現成的退路，要重新啟用 self-hosted runner 或改走 (b)。
- `daily-crawl.yml` 的註解、`README.md`、`docs/ops/daily-crawl.md`、`web/PRODUCT.md` 裡「runner 在筆電、週末屬預期」的說法都要跟著改。
