# 指標的計算只在匯出器，前端只顯示匯出值

攻擊成功率、發球得分率、三項到位率、每局攔網這些指標，「哪個分子除以哪個分母、乘多少、分母為 0 怎麼辦、看哪個次數達浮動門檻」原本寫了好幾份：匯出器三份表（排行榜、球員比率、球隊指標），前端又從原始次數現算球員頁頭條與逐場趨勢，還靠「某個 PR 值是不是空」反推球員哪幾項達門檻。口徑已經走樣：球員比率分母為 0 給 0.0、其他地方沒有值；同一頁的頭條取一位小數、PR 值表取兩位。#122、#168、#319 三張改指標的票每張要同步一到四處，#168 還要回前端手改分母。選項：(a) 只在匯出器算，JSON 連同分子分母一起給，前端只顯示；(b) 兩邊都算，由同一份定義表導出；(c) 只收匯出器，前端不動。決定 **(a)**。

理由：(b) 仍是兩份實作，多一張表要維護；(c) 留下的正是口徑走樣的那兩處。靜態站的資料在建置時就讀進來，多幾個欄位的代價落在建置，不在訪客流量。

同時定下的規則：

- **單一定義在 `src/export/metrics.py`**（#347）：每項指標一筆，記分子欄、分母欄、倍率、看哪個次數、限哪個位置。排行榜、球員比率、球隊指標、球員單場指標都呼叫它。
- **分母為 0 就沒有值**：JSON 是 null，畫面顯示「—」。率類、防守效率與場均項目都適用。
- **指標值連同分子分母一起匯出**：球員賽季與球隊是 `{numerator, denominator, value}`；球員單場是三元組 `[分子, 分母, 值]`。前端的說明文字（「得分 19／40」）只用匯出的分子分母組。
- **達標清單匯出**（`eligible`）：前端不從 PR 值是否為空去反推。
- **全站照匯出的兩位小數顯示**，不補零，前端不再取位。
- **顯示規則留在前端**：各位置看哪些指標、順序、標籤、哪些加「%」。它們決定顯示哪些，不決定怎麼算。

前端仍然自己算的兩處，是寫明的例外：

- 球隊頁「近 3 場與整季比較」：把匯出的分子、分母換一個視窗加總後相除，沒有自己選分子分母。
- 得分來源佔比：各來源得分占總得分的比例，不是技術指標，也沒有第二份定義。

模型特徵（`src/models/features.py`）不併入：它和匯出器只有分子分母欄位相同，分母為 0 給 0.0、不取位、先算單場比率再做 3 場與 5 場滾動平均。把 0 改成沒有值會改變滾動平均，模型要重訓，而現有測試只鎖得住五項特徵中的兩項。

## Consequences

- 加一項指標或改口徑，改 `metrics.py` 一處；前端要動的只剩標籤與顯示位置。
- `box_scores.json` 每列多六個三元組，檔案約為原本的兩倍。單場用三元組而不用物件，是因為 TypeScript 會推斷整個檔的型別：兩萬多列各帶六個含 null 的物件時，型別檢查從 37 秒變成 158 秒、記憶體從 1.5 GB 變成 2.9 GB；三元組是 43 秒。這個檔再長大時，先量型別檢查的耗時。
- 球員頁 PR 值表原本顯示「0%」的項目（分母為 0，多半是非舉球位置的舉球到位率）改成「—」。
- 球員頁頭條與逐場趨勢的率類由一位小數變成兩位。
- 前端要顯示新的比率時，先在匯出器輸出，不在前端相除。
